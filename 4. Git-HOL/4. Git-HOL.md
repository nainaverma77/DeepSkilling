## 1. Theoretical Concepts: Git Merge Conflicts

A **merge conflict** occurs when Git is unable to automatically resolve differences in code between two commits. When merging branches, Git tries to automatically combine changes. If the changes do not overlap (e.g., changes in different files or different lines of the same file), Git performs an automatic merge.

However, a conflict occurs when:
1. **Divergent Changes on the Same Line:** Two branches modify the exact same line(s) of a file in different ways.
2. **File Deletion vs. Modification:** One developer deletes a file while another modifies it.

### Git's Conflict Markers
When a conflict occurs, Git pauses the merge process, marks the files as "unmerged", and inserts special conflict markers into the affected files to help developers identify and resolve the differences:

* `<<<<<<< HEAD`: Starts the section of changes made on the current active branch (the branch you are merging *into*, e.g., `main`).
* `=======`: The separator separating your changes from the incoming branch's changes.
* `>>>>>>> <branch-name>`: Ends the section of changes from the incoming branch (the branch you are merging *from*, e.g., `GitWork`).

### 3-Way Merging
A **3-way merge** uses three commits to generate the merged state:
1. The **Common Ancestor** (the commit where the two branches diverged).
2. **Branch A** (the tip of the target branch).
3. **Branch B** (the tip of the source branch).

Git compares the changes in Branch A and Branch B relative to the Common Ancestor to determine what changes should be integrated. If a line is modified in both Branch A and Branch B compared to the ancestor, Git cannot resolve it automatically, leading to a merge conflict that requires human intervention.

## 2. Visual Diffing & Merging: P4Merge Configuration

Git allows integrating HelixCore **P4Merge** as a graphical tool to resolve conflicts. While graphical tools cannot display interactive interfaces in a headless environment, here is how you configure Git to use P4Merge globally on a local Windows development machine:

1. **Install P4Merge:** Download the installer from Perforce and install it. The default installation path is usually `C:\Program Files\Perforce\p4merge.exe`.
2. **Configure Diff Tool:**
   ```bash
   git config --global diff.tool p4merge
   git config --global difftool.p4merge.path "C:/Program Files/Perforce/p4merge.exe"
   ```
3. **Configure Merge Tool:**
   ```bash
   git config --global merge.tool p4merge
   git config --global mergetool.p4merge.path "C:/Program Files/Perforce/p4merge.exe"
   git config --global mergetool.p4merge.trustExitCode false
   git config --global mergetool.keepBackup true
   ```
4. **Usage:**
   * To check visual differences before merging: `git difftool main..GitWork`
   * To resolve merge conflicts visually: `git mergetool` (this opens the 4-pane P4Merge interface showing the Base, Local, Remote, and Merge output files).

## 3. Hands-on Lab: Step-by-Step Execution

Here is the step-by-step command history, actual terminal output, and explanation for each task in the lab.

### 1. Verify if Master is in Clean State
Check the Git status on the default branch (`main` which acts as master).
* **Command:**
  ```bash
  git status
  ```
* **Actual Output:**
  ```text
  On branch main
  Your branch is up to date with 'origin/main'.
  ...
  ```
  *(Observation: The workspace is pointing to the trunk branch `main`.)*

### 2. Create a Branch `GitWork` and Add a File `hello.xml`
Create the branch `GitWork`, switch to it, and create `4. Git-HOL/hello.xml`.
* **Commands:**
  ```bash
  git branch GitWork
  git checkout GitWork
  ```
* **Actual Output:**
  ```text
  Switched to branch 'GitWork'
  ```
* **Initial `hello.xml` Content:**
  ```xml
  <?xml version="1.0" encoding="UTF-8"?>
  <greeting>
      <message>Hello from GitWork branch!</message>
  </greeting>
  ```

### 3. Update the Content of `hello.xml` and Observe the Status
Modify the content of `hello.xml` and run `git status`.
* **Updated `hello.xml` Content:**
  ```xml
  <?xml version="1.0" encoding="UTF-8"?>
  <greeting>
      <message>Hello from GitWork branch!</message>
      <author>Developer GitWork</author>
  </greeting>
  ```
* **Command:**
  ```bash
  git status
  ```
* **Actual Output:**
  ```text
  On branch GitWork
  Untracked files:
    (use "git add <file>..." to include in what will be committed)
  	4. Git-HOL/
  ```

### 4. Commit the Changes to Reflect in the Branch
Stage the folder contents and commit them to the `GitWork` branch.
* **Commands:**
  ```bash
  git add "4. Git-HOL/hello.xml"
  git commit -m "Add hello.xml on GitWork branch with author info"
  ```
* **Actual Output:**
  ```text
  [GitWork 3722ef6] Add hello.xml on GitWork branch with author info
   1 file changed, 5 insertions(+)
   create mode 100644 4. Git-HOL/hello.xml
  ```

### 5. Switch to Master
Switch back to the trunk branch (`main`).
* **Command:**
  ```bash
  git checkout main
  ```
* **Actual Output:**
  ```text
  Switched to branch 'main'
  Your branch is up to date with 'origin/main'.
  ```

### 6. Add a File `hello.xml` to Master with Different Content
Create `hello.xml` in the same directory but with different tags and content.
* **Conflicting `hello.xml` Content:**
  ```xml
  <?xml version="1.0" encoding="UTF-8"?>
  <greeting>
      <message>Hello from main branch (trunk)!</message>
      <version>1.0.0-trunk</version>
  </greeting>
  ```

### 7. Commit the Changes to the Master
Stage and commit the conflicting file on `main`.
* **Commands:**
  ```bash
  git add "4. Git-HOL/hello.xml"
  git commit -m "Add hello.xml on main branch with version info"
  ```
* **Actual Output:**

  ```text
   create mode 100644 4. Git-HOL/hello.xml
  ```

### 11. Merge the Branch to the Master
Attempt to merge `GitWork` into `main`.
* **Command:**
  ```bash
  git merge GitWork
  ```
* **Actual Output:**
  ```text
  Auto-merging 4. Git-HOL/hello.xml
  CONFLICT (add/add): Merge conflict in 4. Git-HOL/hello.xml
  Automatic merge failed; fix conflicts and then commit the result.
  ```

### 12. Observe the Git Markup
Inspect the conflict markers embedded inside `4. Git-HOL/hello.xml`.
* **Command:**
  ```bash
  cat "4. Git-HOL/hello.xml"
  ```
* **Actual Content:**
  ```xml
  <?xml version="1.0" encoding="UTF-8"?>
  <greeting>
  <<<<<<< HEAD
      <message>Hello from main branch (trunk)!</message>
      <version>1.0.0-trunk</version>
  =======
      <message>Hello from GitWork branch!</message>
      <author>Developer GitWork</author>
  >>>>>>> GitWork
  </greeting>
  ```

### 13. Use 3-Way Merge Tool to Resolve the Conflict
Resolve the conflict. Since we are in a CLI environment, we perform manual 3-way conflict resolution by keeping both useful tags (`version` and `author`) and resolving the text message.
* **Resolved `hello.xml` Content:**
  ```xml
  <?xml version="1.0" encoding="UTF-8"?>
  <greeting>
      <message>Hello from main branch and GitWork branch!</message>
      <version>1.0.0-trunk</version>
      <author>Developer GitWork</author>
  </greeting>
  ```

### 14. Commit the Changes to the Master, Once Done with Conflict
Stage the resolved file and commit to complete the merge.
* **Commands:**
  ```bash
  git add "4. Git-HOL/hello.xml"
  git commit -m "Resolve merge conflict in 4. Git-HOL/hello.xml by combining version and author"
  ```
* **Actual Output:**
  ```text
  [main 3f8365d] Resolve merge conflict in 4. Git-HOL/hello.xml by combining version and author
  ```

### 15. Observe Git Status and Add Backup Files to `.gitignore`
Inspect the status. Often, GUI merge tools like P4Merge create backup files with `.orig` extensions (e.g., `hello.xml.orig`). To prevent committing these, create or append to `.gitignore`.
* **Create/Update `.gitignore` Content:**
  ```text
  # Ignore Git merge tool backup files
  *.orig
  hello.xml.orig
  ```

### 16. Commit the Changes to the `.gitignore`
Stage and commit the `.gitignore` file.
* **Commands:**
  ```bash
  git add "4. Git-HOL/.gitignore"
  git commit -m "Add .gitignore to ignore merge backup files (*.orig)"
  ```
* **Actual Output:**
